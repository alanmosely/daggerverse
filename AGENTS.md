# Agent Notes for daggerverse

Use this as a quick ramp-up for changes in this repo. It covers the
`esp-adf-docker` and `esp-idf` projects (the documented tooling).

## Prerequisites

- Dagger CLI v0.21.8+ (all three `dagger.json` files pin
  `engineVersion: v0.21.8`) and a running Docker daemon.
- All modules use the Python SDK (`sdk.source: python` in each `dagger.json`).

## Repo layout

There are three Dagger modules; run `dagger` commands from the directory
containing the module's `dagger.json` (relative args like `--src .` and
`--project-dir .` resolve against the cwd):

- `esp-adf-docker/` — ESP-ADF Docker image + Dagger module (its
  `dagger.json` sets `source: "dagger"`; Python source lives in
  `esp-adf-docker/dagger/src/main/`). Run from `esp-adf-docker/`.
- `esp-idf/` — Dagger module for ESP-IDF idf.py workflows. Run from
  `esp-idf/`.
- repo root — the `daggerverse` release module (`dagger/` holds its
  source). Run release flows from the repo root; `dagger functions` here
  lists the release module, not esp-idf.

## Module development

- After changing module code or dependencies, run `dagger develop` from
  that module's root to regenerate the `sdk/` bindings.
- Generated, never hand-edit: `*/sdk/` (regenerated by `dagger develop`;
  gitignored and marked linguist-generated), `.venv/`, and each
  `requirements.lock` (regenerate with
  `uv pip compile --universal -o requirements.lock pyproject.toml sdk/pyproject.toml`
  from the directory containing that `pyproject.toml` and `sdk/`:
  `esp-idf/`, `dagger/`, or `esp-adf-docker/dagger/`).
- Hand-written source: `*/src/main/*.py`, `esp-adf-docker/Dockerfile`,
  `esp-adf-docker/entrypoint.sh`, and each `pyproject.toml`.

## esp-adf-docker essentials

- **Purpose**: build and publish an ESP-ADF image based on `espressif/idf`.
- **Version pins** live in `esp-adf-docker/Dockerfile` as `IDF_RELEASE` and
  `ADF_RELEASE`. Keep them compatible with the ESP-ADF README matrix.
- **Entry point** sources `$ADF_PATH/export.sh` so the toolchain is ready
  for interactive shells and CI commands.

## Dagger module

- Module root: `esp-adf-docker/` (source in `esp-adf-docker/dagger/src/main/`)
- API: `build(src)` and `publish(src, token)`
- `registry` and `username` are module constructor args, e.g.
  `dagger call --registry=ghcr.io --username=foo publish ...`
- Publish tag format: `adf-<ADF_RELEASE>-idf-<IDF_RELEASE>`
- Dockerfile is read from `src` relative path (`Dockerfile`).

### esp-adf-docker flows

From `esp-adf-docker/`. Build only:

```bash
dagger call build --src .
```

Publish (Docker Hub PAT in the `DOCKERHUB_TOKEN` environment variable):

```bash
dagger call publish --src . --token env:DOCKERHUB_TOKEN
```

## Conventions and gotchas

- If you change `IDF_RELEASE` or `ADF_RELEASE`, keep the publish tag format
  in sync and update docs.
- Dockerfile uses a shallow clone for speed; avoid removing it unless you
  need full history.
- Keep `entrypoint.sh` minimal; it is run for every container invocation.
- Pass the Docker PAT via `env:DOCKERHUB_TOKEN`; never write tokens to files
  (`.docker-token` remains git-ignored as a safety net).
- All modules set `disableDefaultFunctionCaching: true` in `dagger.json`:
  function results are never served from Dagger's function cache.
  Side-effectful or cache-volume-reading steps additionally set a
  `CACHE_BUSTER` env var (see `release.py` and `config()` in `esp_idf.py`)
  to defeat layer caching — do not remove it.
- Release tags are per-module: `<module>/vX.Y.Z` (e.g. `esp-idf/v0.0.6`).
  Published tags are immutable: never move, delete, or reuse a tag that has
  been pushed — Daggerverse and consumers pin to them.
- Known wart: `esp-idf/v0.0.5` on origin is a stale duplicate of `v0.0.4`
  (same commit). Do not reuse or retarget it; versions continue from v0.0.6.

## How to validate changes

- After module code changes: `dagger develop`, then `dagger functions`
  (from the module root) to confirm the module still loads, and
  `dagger call <function> --help` to check signatures without executing.
  This applies to all three modules, including the repo-root release module.
- For the Docker image itself:
  `docker build -t esp-adf:test esp-adf-docker` then
  `docker run --rm -it esp-adf:test /bin/bash`.

## If you expand documentation

- Prefer updating docs at repo root.
- Note any new tags, env vars, or breaking changes.

## Publishing a module to Daggerverse

`dagger publish` no longer exists; Daggerverse publishes modules from
public git tags. To publish esp-idf:

1. Bump `version` in `esp-idf/pyproject.toml` (next above the highest
   existing `esp-idf/*` tag — check `git tag --list "esp-idf/*"`).
2. Commit, then tag and push:
   `git tag esp-idf/vX.Y.Z && git push origin master esp-idf/vX.Y.Z`.
3. Verify `git rev-parse esp-idf/vX.Y.Z` matches `HEAD` and the tree is
   clean.
4. Submit at <https://daggerverse.dev/publish>, or trigger auto-publish with
   `dagger functions -m github.com/alanmosely/daggerverse/esp-idf@esp-idf/vX.Y.Z`.
5. Optionally create the GitHub release (see below).

## Release automation

- Location: `dagger/src/main/release.py`
- API: `release(tag, ...)` and `release_module(module, version, ...)`
- Uses GitHub API to create releases and optional auto-generated notes.
- Token needs `repo` scope (classic) or Contents read/write (fine-grained).

### Typical flow

From the repo root, after the `esp-idf/vX.Y.Z` tag is pushed:

```bash
dagger call release-module --module esp-idf --version vX.Y.Z --token env:GITHUB_TOKEN
```

This creates a GitHub release for tag `esp-idf/vX.Y.Z` with auto-generated
notes.

## esp-idf essentials

- **Purpose**: run `idf.py` via Dagger using either ESP-IDF or ESP-ADF images.
- **Default image** is `espressif/idf:${DEFAULT_IMAGE_VERSION}` in
  `esp-idf/src/main/esp_idf.py`; `idf_version` is ignored when
  `adf_version` is set.
- **ADF image**: bare tags (no `/`, e.g. `adf-v2.7-idf-v5.3.4`) resolve
  against the `adf_image_repo` constructor arg (default
  `alanmosely/esp-adf`); override with
  `dagger call --adf-image-repo=you/esp-adf run ...`. Any value containing
  `/` is used verbatim as the image reference.

## esp-idf module

- Location: `esp-idf/src/main/esp_idf.py`
- API: `run`, `build`, `config`, `docs`, `flash`
- `build` returns the `build/` directory for export.
- `run`, `build`, `config`, and `flash` accept `target` to run
  `idf.py set-target` first (`docs` supports neither `target` nor
  `adf_version`).
- Compilation uses ccache via the `esp-idf-ccache` Dagger cache volume
  (`IDF_CCACHE_ENABLE=1`, `CCACHE_DIR=/ccache`).
- `config` runs `idf.py fullclean` then `menuconfig` in an interactive
  terminal session and returns the resulting `sdkconfig` file (staged via a
  cache volume, since terminal sessions are ephemeral). `/staging/sdkconfig`
  is cleared at session start so a stale config is never returned; if the
  session aborts before completing (non-zero exit, killed terminal), the
  staged copy fails rather than returning stale data.
- `flash` connects to RFC2217 on `serial_host`/`serial_port`.

### esp-idf flows

From `esp-idf/`, with `--project-dir` pointing at a real ESP-IDF firmware
project (note `--project-dir .` would mount the module directory itself).
Build:

```bash
dagger call run --project-dir <your-project> --idf-args build
```

Build and export artifacts:

```bash
dagger call build --project-dir <your-project> export --path ./build
```

Menuconfig (exports the resulting sdkconfig):

```bash
dagger call config --project-dir <your-project> export --path ./sdkconfig
```

Flash (RFC2217):

```bash
dagger call flash --project-dir <your-project> --serial-host host.docker.internal --serial-port 4000
```

## esp-idf gotchas

- `config` is interactive and requires a TTY; run it from a terminal.
- `flash` requires an RFC2217 server on the host. The helper script is
  Windows-only and needs `pyserial`.

## esp-idf validation

- `dagger functions` (from `esp-idf/`)
- `dagger call build --help` and `dagger call flash --help`
- `dagger call run --project-dir <your-project> --idf-args build` against a
  real ESP-IDF project (create one with `idf.py create-project`); there are
  no automated tests in the repo.
